# Generation resolution for queued jobs

Extend the settings contract from [plan 04](04-generation-settings.md) with a batch-wide `pipeline_type` string. Every job stores the resolved mode and uses it when dispatched. Keep 512³ as the default for omitted settings and existing jobs.

| Value | Requested grid | Generation path |
| --- | --- | --- |
| `"512"` | 512³ | Single pass at 512³ |
| `"1024"` | 1024³ | Direct generation from a finer coarse structure |
| `"1024_cascade"` | 1024³ | 512³ shape followed by high-resolution refinement |
| `"1536_cascade"` | 1536³ | 512³ shape followed by high-resolution refinement with a sparse token budget |

## Upload, storage and dispatch

1. Add the four exact strings to the existing JSON `settings` text part of `POST /jobs`. Reject unknown strings, numbers, and null with HTTP 400 and `invalid_settings`. Preserve batch atomicity and the current multipart limits. Document all values and the default in OpenAPI and the generation README. Return the resolved `settings.pipeline_type` in submission acknowledgements, list responses, and job details.
2. Treat a missing `pipeline_type` in an existing saved settings object as the fixed legacy value `"512"`. Existing records without a settings object still use the legacy defaults. Keep malformed explicit values invalid. Dispatch the existing frozen settings snapshot through the supervisor and pass its mode explicitly to `pipeline.run`. Preserve FIFO, one active job, seed, sampler overrides, and GLB export options. Back up the data volume before deployment if rollback is needed. The previous service uses strict record validation and rejects the new fields once they are written. [Settings model](../generation/settings.py) · [Job store](../generation/store.py) · [Supervisor](../generation/supervisor.py)
3. Keep the current 512 startup path and low-VRAM offloading. On the first job that needs high-resolution models, resolve the two `_1024` flow checkpoints from the loaded pipeline's pretrained configuration. Reuse the base loader's checkpoint path resolution and Hugging Face cache. Load both into temporary CPU references and call `.eval()` on each before adding the complete pair to the pipeline. Reuse the pair while the measured system RAM budget permits. If retaining both makes subsequent jobs unstable, test eviction and reload or loading one high-resolution model at a time. Keep all four modes valid and selectable. A checkpoint download/load failure fails that job with a clear message. A CUDA OOM fails the job and triggers existing worker replacement. A job never retries in a different mode. [Checkpoint loading](../trellis2/pipelines/base.py) · [Pipeline requirements](../trellis2/pipelines/trellis2_image_to_3d.py#L522) · [Worker](../generation/worker.py)
4. Emit a `loading_checkpoints` stage before `preparing_image` when the worker loads extra weights. Include it in the shared stage order and stub fixtures. Later jobs with cached models can skip that stage.

## Actual output resolution

- Store `actual_resolution` as a separate nullable integer on the job. Report it in acknowledgement, history, and detail responses. Old jobs and jobs without a successful export can have null. Read the actual grid from the pipeline output's voxel size (`round(1 / mesh.voxel_size)`), which is assigned from the decoder resolution. Verify that it is valid for the selected mode before promoting the GLB. [Decoded mesh resolution](../trellis2/pipelines/trellis2_image_to_3d.py#L482)
- Keep the current sparse token budget of 49,152. A 1536³ request can produce 1536³, 1408³, 1280³, 1152³, or 1024³. The pipeline accepts intermediate grids below the threshold and stops at 1024³ even if still over it. Both 1024³ modes must report 1024, and 512³ mode must report 512. Treat missing or mismatched resolution metadata in a new completion message as a failed job and keep the store available. Store the original mode regardless of the achieved grid. Leave the token budget under service control. [Cascade token budget](../trellis2/pipelines/trellis2_image_to_3d.py#L330)
- Extend the worker's artifact completion message with the actual grid. After validating the partial GLB, durably record the grid before promoting the artifact so restart recovery can retain the value if the process exits after rename. Use the updated job for both the supervisor's active reference and final success write. Clear the grid when a new-format job fails without a valid promoted GLB. Use a shared public serializer for submission, list and detail responses to report null until success, even if the store already has the value for recovery. Keep existing downloads and recovery rules. [Artifact promotion](../generation/supervisor.py#L92) · [Restart recovery](../generation/store.py#L180)

## Verification

- With a stub worker, test all modes, images-only and partial settings uploads, malformed values and completion metadata, multiple batches, restart with older records, and worker replacement. Verify that a 1536³ request can publish an actual grid of 1280³ and survives restart. Exercise interruptions on both sides of artifact promotion. Simulate a worker disappearing during a high-resolution job, as can happen when Docker runs out of system RAM. Verify existing worker-loss handling fails that job and the next queued 512³ job can still run.
- On the 12 GB RTX 3060, run one worker at a time. Test the first high-resolution load, a warm repeat, and a 512³ job after the high-resolution pair is resident. Test all four modes on representative simple and detailed images, then the highest export and sampling settings on feasible modes. Record model loading and generation times, peak Docker/WSL system RAM and VRAM, requested/actual grids, and GLB validity. Verify in Blender that face data and embedded materials survive export. Record failures by mode and stage. Completion depends on the image and available resources.
